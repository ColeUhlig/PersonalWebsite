Following ten dollars through Farmerdrop

Farmerdrop customers order produce from local farms and collect it from a neighbour's porch, the drop host. The customer pays on Tuesday. The farmer picks and packs on Thursday, drives the crate to the drop host on Friday, and the customer collects it on Saturday.

So for four days Farmerdrop holds money for food that, at first, hasn't been picked. I built the payment system around one question: at every moment, who owns each cent, and where is the crate? The bar pinned to the top of this page answers both as you scroll.

Where the $10 goes

The split isn't calculated in application code. It's a Postgres function, compute_order_financials, and the rates it uses are copied onto the order when it's placed, so changing a fee next month can't change what this order owes anyone. Card and payout fees come out of each payee's share instead of being added to the customer's bill, and Farmerdrop keeps whatever is left, so the five pieces always add up to exactly $10.00.

Taking the payment

Stripe charges the card, but Stripe doesn't know who the money belongs to. That's my ledger's job. The hard part is the moment between the two: the card has been charged and my ledger doesn't know yet.

Write it down, then call Stripe

Before my server asks Stripe for anything, it writes a row to an outbox table, stripe_transactions, under an idempotency key made of the order IDs and the amount. The same key goes to Stripe. If anything fails after this, a retry finds the same row and Stripe hands back the same PaymentIntent, so the customer can never be charged twice.

The card is charged, and my books don't know

The browser sends the card straight to Stripe; card numbers never touch my server. Stripe charges $10.00 into Farmerdrop's balance. Look at the bar above: the money exists, but nothing in my ledger says so. This gap is where payment bugs live.

Two messengers, one door

Two messages now head to my server: the browser's mark-paid call and Stripe's payment_intent.succeeded webhook. Neither is taken on trust. The webhook's signature is checked, and mark-paid asks Stripe whether the payment really succeeded. Both then call the same function, applySucceededPaymentIntent.

Book it, exactly once

In one database transaction the function locks the order's row, writes the ledger entries and marks the order paid. Stripe's fee (2.9% + 30¢) is set aside, Farmerdrop keeps 25¢ of the finance fee now, and the other $9.16 goes to Held for the order: money that belongs to the order, not to any person yet. Nobody has earned it, because the tomatoes are still on the vine.

What if the customer closes the tab right after paying?

The card is charged

Same as before: the customer confirms, and Stripe takes $10.00.

Neither messenger arrives

The tab closes before the browser can call mark-paid. And say the webhook fails too: my server is mid-deploy, or the endpoint returns an error. Stripe keeps retrying for up to three days, but for now the money is at Stripe, my ledger is empty, and the order still says "processing".

A job that doesn't wait to be told

Every five minutes a scheduled job looks for orders stuck in "processing" and asks Stripe directly what happened to each one. It doesn't need the browser or the webhook. Orders left unpaid for 30 minutes get cancelled, but only after this same check, so a slow payment is never cancelled while it's actually paid.

Booked through the same door

Stripe says it succeeded, so the job calls the same applySucceededPaymentIntent. The ledger now matches reality, at most about five minutes late.

The late webhook changes nothing

When Stripe's retry finally lands, the order is already paid, so the function does nothing. Four doors lead to the booking (the browser, the webhook, the app's redirect and this job), and whichever arrives first wins.

What if the webhook and the browser arrive at the same moment?

Two requests, milliseconds apart

This is the normal case, not an edge case. The browser usually wins, but the webhook is often close behind.

Both ask for the same lock

Each request opens a transaction and runs SELECT … FOR UPDATE on the order's row. Postgres gives the row to one of them; the other waits.

One books, one walks away

A writes the ledger, marks the order paid and commits. Only then does B get the row, see "paid", and return without touching anything.

A backstop, and the bug behind it

A partial unique index allows one payment row per order, so even a path that skipped the lock couldn't book twice. I built all this after finding that the normal desktop flow booked nothing: mark-paid used to flip the order to paid without writing the ledger, and the webhook then skipped it as already paid. All 760 tests passed, because every test entered money through the webhook.
